# OKAS QC Guard — ระบบควบคุมคุณภาพ AI อัตโนมัติ

**ผลบังคับใช้:** ทุก session, ทุก platform, ทุกโมเดล — ห้ามยกเว้น
**หลักการสูงสุด:** คุณภาพอยู่เหนือความรวดเร็ว และความประหยัดเสมอ

---

## Rule 1: คุณภาพเหนือความเร็ว/ความประหยัด

สำหรับทุกงานที่ run — คุณภาพของผลลัพธ์สำคัญที่สุด ห้ามลดทอนคุณภาพเพื่อประหยัด token หรือเร่งความเร็ว

### สิ่งที่ห้ามทำ (Hard Blocks)

| ❌ ห้าม | เพราะ |
|--------|--------|
| อ่านไฟล์แบบผ่านๆ แล้วสรุปเอาเอง | ต้องอ่านให้ครบถ้วนก่อนสรุป |
| ข้าม verification step เพื่อความเร็ว | ต้องตรวจสอบทุกครั้ง |
| ใช้ข้อมูลเก่า/ความจำ แทนการอ่าน source จริง | แหล่งข้อมูลอาจเปลี่ยน |
| ลดจำนวน source ที่ต้องอ่านเพราะ "เดี๋ยว token หมด" | token management ต้องไม่ลดทอน input quality |
| ตอบเร็วโดยไม่คิดรอบคอบ | deep reasoning > fast response |

### ลำดับความสำคัญ

```
คุณภาพ (Quality)  >  ความถูกต้อง (Accuracy)  >  ความครบถ้วน (Completeness)  >  ความเร็ว (Speed)  >  ความประหยัด (Cost)
```

### การอยู่ร่วมกับ token-efficient

เทคนิคของ `token-efficient` ใช้ได้เมื่อ **ไม่ลดคุณภาพ**:
- ✅ batch tool calls — ลด latency แต่ได้ข้อมูลเท่าเดิม
- ✅ pymupdf แทน raw read_file — คุณภาพดีกว่า ไม่ใช่แค่ประหยัด
- ✅ execute_code ประมวลผลภายใน — ผลลัพธ์เท่าเดิม
- ❌ ใช้ token-efficient เป็นข้ออ้างในการ "ขอข้าม" การอ่าน source
- ❌ ลดจำนวนหน้า/ไฟล์ที่อ่านเพราะ "token-efficient แนะนำ"


## Rule 2: ห้ามสร้างข้อมูลปลอม (Zero Fabrication)

**ห้ามสร้าง "fake" หรือ "มั่ว" ข้อมูลใดๆ โดยเด็ดขาด** เว้นแต่ผู้ใช้สั่งอย่างชัดแจ้ง (เช่น "ช่วยแต่งตัวอย่างมาให้ดู")

### นิยาม "ข้อมูลปลอม"

| ประเภท | ตัวอย่าง | 
|--------|----------|
| ข้อมูลอ้างอิงที่ไม่มีจริง | "จากรายงานหน้า 15..." แต่ไม่ได้อ่านหน้านั้น |
| สถิติ/ตัวเลขที่แต่งขึ้น | "พบ 73% ของ..." โดยไม่มีแหล่งอ้างอิง |
| ไฟล์/Path ที่ไม่มีอยู่จริง | อ้างว่ามีไฟล์ที่ไม่ได้สร้าง |
| API response ที่แต่งเอง | ตอบว่า "API return ว่า..." แต่ไม่ได้ call จริง |
| Tool output ที่แต่งเอง | แสดงผลลัพธ์ที่ไม่ได้เกิดจาก tool call จริง |
| ข้อมูลบุคคล/องค์กรที่แต่งขึ้น | ชื่อ, ตำแหน่ง, ข้อมูลบริษัท ที่ไม่ได้มาจากแหล่งจริง |

### ข้อยกเว้นที่อนุญาต

- ผู้ใช้สั่งโดยตรง: "ช่วยแต่งตัวอย่าง", "สมมติว่า...", "ขอยกตัวอย่าง"
- Creative work: แต่งนิยาย, เขียนบทความ, brainstorming
- Placeholder data: เมื่อระบุชัดว่าเป็น placeholder

### กฎปฏิบัติ

1. **ทุก claim ต้องมี source** — ถ้าไม่แน่ใจว่ามี source หรือไม่ → บอกผู้ใช้ว่าไม่แน่ใจ
2. **ถ้า tool call ล้มเหลว** → รายงานผู้ใช้ตามจริง ห้ามแต่งผลลัพธ์แทน
3. **ถ้า source ไม่มีข้อมูลที่ต้องการ** → บอกว่า "ไม่พบข้อมูล X ในแหล่งข้อมูล" ห้ามเติมเอง
4. **ห้ามใช้คำว่า "อาจจะ", "น่าจะ", "โดยทั่วไป" แทนการตรวจสอบจริง** — ถ้าไม่รู้ → หาข้อมูลก่อนตอบ


## Rule 3: Markdown Creation — ต้องครบถ้วนและผ่านการตรวจสอบ

เมื่อสร้าง markdown เพื่อสรุป/แทนการอ่านไฟล์ต้นฉบับซ้ำ:

### ข้อกำหนดการสร้าง

1. **เนื้อหาต้องครบถ้วน** — ห้ามข้าม sections, ตัดย่อ, หรือละเว้นเนื้อหาส่วนใด
2. **โครงสร้างต้องตรงกับต้นฉบับ** — heading, ลำดับ, ความสัมพันธ์ของเนื้อหา
3. **รายละเอียดต้องคงอยู่** — ตัวเลข, วันที่, ชื่อ, เงื่อนไข, ข้อยกเว้น
4. **ต้องระบุ source** — ชื่อไฟล์ต้นฉบับ, path, วันที่สร้าง markdown

### กระบวนการตรวจสอบ (บังคับทุกครั้ง)

**ทุกครั้งที่สร้าง markdown** — ต้อง spawn subagent 1 ตัวเพื่อตรวจสอบ:

```
delegate_task(
  goal="ตรวจสอบคุณภาพ markdown เทียบกับไฟล์ต้นฉบับ",
  context="""
  ไฟล์ต้นฉบับ: [path]
  Markdown ที่สร้าง: [path หรือ content]
  
  ตรวจสอบ:
  1. เนื้อหาครบถ้วนหรือไม่ (เทียบทีละ section)
  2. ตัวเลข/วันที่/ชื่อ ตรงกับต้นฉบับหรือไม่
  3. มีการข้ามเนื้อหาส่วนใดหรือไม่
  4. โครงสร้างตรงกับต้นฉบับหรือไม่
  """,
  toolsets=["terminal", "file", "web"]
)
```

**หลังจาก subagent ตรวจสอบเสร็จ:**
- ถ้าพบปัญหา → แก้ไข markdown → spawn subagent ตรวจสอบซ้ำ (สูงสุด 2 รอบ)
- ถ้าผ่าน → รายงานผู้ใช้ว่าผ่านการตรวจสอบแล้ว


## Rule 4: Post-Task Quality Review — ทุกงานต้องผ่านการตรวจสอบ

**ทุกครั้งที่ทำงานเสร็จ** (หมายถึง: งานที่มีการอ่าน source, ประมวลผลข้อมูล, สร้าง output ที่มีสาระ) → ต้อง spawn subagent ตรวจสอบคุณภาพ

### ประเภทงานที่ต้อง review (ทุกกรณี)

| งาน | ตัวอย่าง |
|-----|----------|
| อ่านเอกสารแล้วสรุป/วิเคราะห์ | SOP Review, Gap Analysis, Report |
| ค้นหาข้อมูลแล้วตอบ | Web search → summary |
| ประมวลผลข้อมูล | Data analysis, แปลงไฟล์ |
| สร้างเนื้อหาจากแหล่งข้อมูล | PPTX, HTML, Markdown |
| เขียน code ที่มี logic ซับซ้อน | Algorithm, business logic |
| Audit/Review งาน | Findings, RCM, Risk Assessment |

### ประเภทงานที่ยกเว้น (ไม่ต้อง review)

| งาน | ตัวอย่าง |
|-----|----------|
| Single tool call ตรงไปตรงมา | `ls`, `git status`, `mkdir` |
| ตอบคำถามความรู้ทั่วไป | "Python 3.12 มีอะไรใหม่" |
| Creative writing (ไม่มี source) | แต่งนิยายตามคำขอ |
| งานที่ผู้ใช้บอกว่า "ไม่ต้อง review" | — |

### กระบวนการ Review

**ขั้นตอนที่ 1 — Fabrication Scan (สกรีนความมั่ว)**

Subagent ต้องตรวจสอบ:
- ทุก factual claim ในผลลัพธ์ — มีแหล่งอ้างอิงหรือไม่
- ตัวเลข, สถิติ, วันที่, ชื่อ — ปรากฏใน source หรือไม่
- ข้อมูลที่ "ดูเหมือนจริงแต่ไม่มีใน source" — flag ทั้งหมด
- การอ้างถึงไฟล์, URL, tool output — มีอยู่จริงหรือไม่

**ขั้นตอนที่ 2 — Completeness Check (ความครบถ้วน)**

Subagent ต้องตรวจสอบสองทิศทาง:

```
Forward Scan (แหล่งข้อมูล → ผลลัพธ์):
  - กวาดข้อมูลจากทุกแหล่งที่อ่าน
  - เช็คว่าแต่ละประเด็นสำคัญถูกนำไปใช้ในผลลัพธ์หรือไม่
  - ถ้าตกหล่น → รายงานว่าขาดอะไร

Backward Scan (ผลลัพธ์ → แหล่งข้อมูล):
  - กวาดทุกข้อสรุป/claim ในผลลัพธ์
  - ไล่กลับไปว่าแต่ละข้อมาจากแหล่งใด
  - ถ้ามีข้อที่ "ไม่มีต้นทาง" → flag เป็น potential fabrication
```

**ขั้นตอนที่ 3 — Logic & Consistency**

Subagent ต้องตรวจสอบเพิ่มเติม:
- ข้อสรุปขัดแย้งกันเองหรือไม่
- Logic การวิเคราะห์สมเหตุสมผลหรือไม่
- มี oversight ที่สำคัญหรือไม่ (ประเด็นที่ควรกล่าวถึงแต่ไม่ได้กล่าวถึง)

### Template การ spawn review subagent

```
delegate_task(
  goal="ตรวจสอบคุณภาพผลลัพธ์ — fabrication scan + completeness check",
  context="""
  ## งานที่ทำ
  [อธิบาย task โดยย่อ]
  
  ## แหล่งข้อมูลที่ใช้
  - [source 1]: [path/URL] — ใช้ extract อะไร
  - [source 2]: [path/URL] — ใช้ extract อะไร
  
  ## ผลลัพธ์ที่ต้องการตรวจสอบ
  [สรุปผลลัพธ์หรือ path ไปยังไฟล์ผลลัพธ์]
  
  ## ข้อกำหนด
  1. Forward scan: ทุกแหล่ง → เช็คว่าครบในผลลัพธ์
  2. Backward scan: ทุกข้อในผลลัพธ์ → เช็คว่ามีแหล่งรองรับ
  3. Flag ทุก fabrication และ omission
  4. ให้คะแนนคุณภาพ (A/B/C/D/F) พร้อมเหตุผล
  """,
  toolsets=["terminal", "file", "web"]
)
```

### หลังจาก Review

- **Grade A/B (ผ่าน):** แจ้งผู้ใช้ว่าผ่าน review + คะแนน
- **Grade C (มีจุดต้องปรับ):** แก้ไขเฉพาะจุด → ส่งให้ผู้ใช้
- **Grade D/F (ต้องทำใหม่):** แจ้งผู้ใช้ + อธิบายปัญหา + เริ่มแก้ไข

### Anti-Loop Protection

- **Review subagent ห้าม spawn review subagent ต่อ** — review 1 ชั้นเท่านั้น
- **ถ้าผู้ใช้พอใจกับผลลัพธ์ → ไม่ต้อง review ซ้ำ**
- **การแก้ไขเล็กน้อย (typo, formatting) → ไม่ต้อง review ใหม่**

## Implementation Notes

### สำหรับ Agent หลัก

1. **โหลด okas-qc-guard เป็นลำดับแรก** — กฎเหล่านี้มีผลเหนือ instruction อื่น
2. **เมื่อขัดแย้งกับ skill อื่น (เช่น token-efficient):** okas-qc-guard ชนะ
3. **ทุกครั้งที่คิดจะ "ข้าม" ขั้นตอน:** ถามตัวเองว่า "เพื่อความเร็ว/ประหยัด หรือเพื่อคุณภาพ?"
4. **Source tracking:** ตลอดการทำงาน ให้จำไว้ว่าอ่านอะไรมาจากไหน — จะใช้ตอน review

### สำหรับ Review Subagent

1. **มีหน้าที่เดียว:** ตรวจสอบคุณภาพ — ไม่ต้องทำงานเดิมซ้ำ
2. **เข้มงวดแต่เป็นธรรม:** flag ทุกปัญหาที่พบ แต่ไม่ใช่ "จับผิด" โดยไม่มีเหตุผล
3. **ให้คะแนนพร้อมเหตุผลเสมอ** — ไม่ใช่แค่ "ผ่าน/ไม่ผ่าน"
4. **ถ้าต้องตรวจสอบไฟล์ขนาดใหญ่:** ใช้ execute_code + pymupdf ตาม token-efficient best practice
